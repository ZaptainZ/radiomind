# 2026-08-10 称呼线索（§4）—— 把开放题变成点一下

> 需求：HackWare `projectBasicInfo/handoff-ask-identity.md` §4。
> 解锁前提由 owner 确认：episode 已干净（128/128 有绝对时间、participants 最多 5 人且全是稳定 label），
> 素材里确有称呼（「与庆松、明月约好晚上吃烧烤」「因误将明月看成明天」）。

## 为什么值得做

`pending-questions` 里 name 类问题的 `options` 一直是空的，只能问开放题。
开放题在手机上要打字要回忆，是非题只要点一下——这是体验上一个数量级的差别，
而素材本来就躺在生活日志里。

## 交付

```
speakers name-hints prepare        # 组料 + 提示词，交给宿主 LLM
speakers name-hints apply          # 收回名字列表 → 共现统计 → 存为候选
speakers name-hints auto           # 本机有 LLM 时一步到位（R76S 裸 CLI 没有）
```

候选存进 `speakers.metadata.name_candidates`（**没有新建表、没有动 schema**，
`metadata` 这个列存在就是干这个的），`pending-questions` 读它来填 `options`。

测试 **1177 → 1191 passed**，regression pack 新增 `speakers:name-hints`，全绿。

## 核心判断：LLM 只做语义，统计留在本地

看了生产真实 summary 之后定的。真实文风长这样：

> 乘客在四季青桥站台等车……提及与庆松、明月约好晚上吃烧烤……提及吃过的狮子头很好吃
> ……发言人1D提出可尝试反向打光

**正则抽人名在这种文本上必然失败**：`四季青桥`（地铁站）、`狮子头`（菜）、`明天`（时间词）
和`明月`（人）在字面上无法区分，而 `发言人1D` 这类分段标记**即使 participants 已经清干净了、
仍然漏在 summary 正文里**。区分它们需要语义，这正是项目「宿主 LLM 优先、放弃本地小模型/正则抽取」
那条既有结论的适用场景。

但**归属不需要语义**。名字集合一旦拿到，「这名字是谁的」就是数数：
`participants` 现在是干净的稳定 label 列表，直接数共现即可。于是分工定为：

- **LLM**：哪些词是人名（唯一不可约的语义任务，输出是一个短列表，容易校验）
- **本地**：这名字属于谁（纯算术，可复现、可审查）

好处不只是省钱：LLM 的输出面积缩到最小，出错也容易发现。

## 排序指标换过一次 —— 这个坑是 smoke 抓到的，单测没抓到

最初用 **lift**（`P(名字|说话人在场) / P(名字)`）判定强弱。单测全过。
但 CLI smoke 一跑，**唯一该成为按钮的「明月」落成了弱候选**：
support=2、lift=1.33 < 阈值 1.5，于是这个功能存在的意义本身没被兑现。

根因：lift 是对基线的比值，**episode 少的时候会发软**——「明月」在 4 条里被提 3 次，
基线本来就高，比值自然上不去。

换成一个更钝也更稳的问题：**这名字被提到的那些次里，这位说话人在场的比例是多少**
（`support / name_episodes`）。「明月」被提 3 次、spk_003 在场 2 次 = 0.67。
判定改成 `support >= 2 且 precision >= 0.6`：

| 候选 | support | precision | 结果 |
|---|---|---|---|
| 明月 → spk_003 | 2 | 0.67 | **强**，成为按钮 |
| 狮子头 → spk_003（模型幻觉） | 1 | 1.0 | 弱，只留证据 |
| 庆松 → spk_001（被提及但不在场） | 1 | 1.0 | 弱，只留证据 |

lift 保留下来做**入选过滤**（`>= 1.2`），它擅长的是另一件事：踢掉「到处都出现、
因而对判断谁在场毫无信息量」的词。两个指标各司其职。

**教训**：这个缺陷单测抓不到，因为单测的期望是我照着自己的实现写的。
是拿贴近生产文风的数据跑 CLI 才暴露的。

## 弱候选：记录，但不给按钮

owner 的要求是「边界情况标低置信度而不是硬塞」。我把它拆成两层：

- **证据里保留全部候选**（含 support / precision / lift / 哪几条 episode / 哪几天），
  owner 拿不准时能看出依据；
- **按钮只放强候选**。理由：手机上误点一下就写进一个错名字，而且弱候选会稀释真候选。

所以「都不是」只在有按钮时出现，`answer_type` 相应地是 `choice_or_text` 或 `text`——
**有按钮也永远接受自由文本**，候选是捷径不是全集。

## 两个坑（owner 点名的）

- **「我」不是名字**，佩戴者已由 `is_wearer` 定死。`parse_response` 里有一张
  「永远不是名字」表（`我 / 自己 / 对方甲 / 发言人X / spk_NNN`）**在代码里过滤**，
  不依赖提示词——模型会在正文里看到这些标记，可能原样吐回来。
- **被提及 ≠ 在场**。「与庆松、明月约好」说的是不在场的人。precision + support
  拦住了大部分；边界情况标低置信度。

## 一条不变量

**这里从不写 `display_name`。** 候选永远只是提案，命名是 owner 的一次明确动作。
被谈论和在场是两回事，只有 owner 能合上这个缝。
